# 实施路线图

当前仅完成调研文档。本路线图不代表已获准启动安装、真实账号操作或系统定时配置。

深入调研后的优先级：Playwright 本地执行器作为主线，QD 仅作为安全调整后的 HTTP 备选。P0—P1 必须先验证 Cookie 轮换、TLS、跨域跳转和日志／导出数据流，具体实验见 [深入调研](./DEEP_DIVE.md)。不同时建设两套正式系统。

## 交付目标

在 macOS 上先交付一个本地运行、可每日／每周调度、可维护多个站点流程的工具，再验证 Windows。用户通过本地网页管理；常规运行不依赖云端模型或第三方验证码服务。

可扩展性验收以“新增流程不修改调度和凭据核心”为标准，不以“任意网站零配置”作为标准。

## P0：真实站点取样与最终选型

投入估算：0.5—1.5 个工作日；依赖用户提供目标站点及可用登录方式。

- 选择 3—5 个优先站点，包括简单签到、多步每日任务、至少一个验证场景。
- 记录入口、任务步骤、完成标志、日／周刷新时间、认证域名、验证出现时机。
- 核实系统版本与 CPU 架构，确认 Playwright 版本支持范围。
- 固定 QD、Playwright 等试点版本和依赖来源，审阅准备复用的文件与许可。
- 在后续获准实施时比较 QD 与最小浏览器流程，不先开发完整界面。

退出条件：形成逐站可行性矩阵，明确“自动／需人工／暂不支持”；选定主路线。如果所有目标均能用 QD 可靠完成，则优先复用 QD。

## P1：本地执行与认证闭环

投入估算：2—4 个工作日。

- 实现单个账号的手动登录、认证状态保存、重新登录、清除状态。
- 实现一个 HTTP 签到和一个浏览器签到适配器，CLI 先行便于调试。
- 默认不保存密码；可选密码登录必须完成域名绑定、秘密存储和日志脱敏后再启用。
- 提供结构化执行结果，区分已签到、失败、需要验证、结果未知。

验收：

1. 退出并重新启动工具后，在会话仍有效时可复用登录态。
2. 登录过期时不误报成功、不反复提交密码。
3. 同一天重复运行可识别已完成。
4. 测试秘密不会出现在日志、Git 文件或不允许的网络目的地。

## P2：每日／每周调度及 Mac 恢复运行

投入估算：1—2 个工作日。

- 数据库存储计划、时区、周期键、最近运行和下一次到期时间。
- 添加 Mac 用户级启动配置，以及明确可卸载的步骤。
- 支持每天、每周指定日、手动运行、暂停、在有效窗口内补跑。
- 运行锁、重试上限、异常退出恢复；只保留一套权威调度状态，避免 OS 和应用重复触发。
- 关机跨过任务窗口时记为错过，不伪造昨日补签。

验收：覆盖进程退出、电脑休眠／唤醒、重启、断网、重复触发、跨日／跨周边界；每个场景有预期和实际结果记录。

## P3：多步骤任务与人工接管

投入估算：2—4 个工作日。

- 建立适配器协议与声明式步骤，支持条件分支、动态 token、任务依赖和进度检查。
- 将两种不同流程接入统一状态机，验证核心不需要随站点变化修改。
- 检测到验证后暂停，通知用户；给出打开任务／继续／手动完成入口。
- 人工操作和后台执行互斥，防止同一浏览器被两方同时控制。
- 人工接管超时释放资源，重新开始时核对状态与 token，不能沿用过期表单。
- 如自动化浏览器无法通过验证，允许该次任务降级为手工完成并记录原因。

验收：一个多步骤任务中断后不会重复已经确认完成的动作；至少一个真实验证场景有明确恢复结果。只有模拟验证通过，不计作真实网站通过。

## P4：本地管理页面与 Windows 验证

投入估算：2—4 个工作日。

- 页面仅保留站点、计划、结果、需要处理、设置等必要入口。
- 加站点向导、一次登录、试运行、最近失败原因、无秘密配置导入导出。
- 本地面板访问控制、CSRF 和跨域检查。
- Windows 任务计划程序适配，验证路径空格、权限、凭据存储、进程退出和用户会话。
- 输出 Mac 与 Windows 的安装、启动、更新、卸载说明。

验收：非开发者无需手改 Cookie 或源码即可配置已支持站点。Windows 若缺实机，只能标“待验证”，不能写“两端已调试通过”。

## P5：持续运行与交付

观察时间：至少连续 7 个自然日；周任务至少跨过两个真实周周期。工程投入另计约 1—2 个工作日。

- 固定版本连续执行，记录每次是否启动、是否完成、是否需人工及原因。
- 演练备份恢复、会话撤销、日志清理、任务停用和卸载。
- 每站公布支持方式、最近验证日期、已知限制；适配器升级后只重测相关流程与核心回归。

验收不混淆两个指标：

| 指标 | 计算与要求 |
|---|---|
| 调度触发率 | 在线且运行环境满足条件时，实际启动次数／应启动次数；试运行窗口要求全部触发 |
| 无人值守完成率 | 无人工完成次数／有效计划次数，按站点报告，不预先承诺百分比 |
| 人工协助完成率 | 需要协助后最终完成的次数单列 |
| 误报成功 | 验收样本中必须为 0 |
| 重复副作用 | 重复触发与中断测试中必须为 0；无法查询状态的任务应停止并标未知 |
| 凭据外传 | 测试中禁止向非批准认证目的地发送秘密 |

环境不满足的运行不能从报告中消失：关机、用户未响应、站点不可用等原因单列，以便看清真实使用体验。

## 工期、成本与决策门槛

自研路线粗估合计 9—18 个工程工作日，另加实际观察周期；这是单人开发量级估算，不是交付承诺。目标站点复杂度、系统版本与验证码频率会显著改变投入。若 QD 能满足试点需求，范围可缩小为配置、适配和运行验证。

本地默认路线不需要按次调用付费模型或验证码 API；成本主要是浏览器运行、依赖安装和站点变更维护。首版不购买云服务器。

如果多数核心站点每次都强制人机验证且拒绝自动化浏览器，应优先交付“自动打开任务＋人工完成＋结果管理”，重新评估全自动目标，避免持续投入到不可保证的绕过路线。

## 下一阶段需要的输入

不需要在聊天中发送密码。先提供以下非敏感信息即可：

| 信息 | 示例 |
|---|---|
| 最优先的 3—5 个网址 | 论坛首页与签到／任务入口 |
| 每站要完成的动作 | 点击签到、阅读任务、领取奖励、每周任务 |
| 验证频率与类型 | 登录时扫码、每天滑块、偶发 Turnstile |
| 运行电脑 | macOS 版本与芯片；Windows 版本 |
| 在线习惯 | 白天开机、晚上休眠，或有常开设备 |
| 凭据策略 | 手动登录复用状态，或允许仅向目标认证站发送密码 |
| 人工协助容忍度 | 偶尔重新登录可以，还是必须完全无人值守 |

不确定的字段先标未知，后续站点验证时补齐。用户授权进入开发阶段后再执行 P0—P1。
