# 网页论坛签到与每日任务自动化调研

日期：2026-10-20。范围：公开开源仓库、部分源码与依赖文件、官方技术文档。本文是选型调研，不是已调试成功的交付说明。

后续更新：已完成 [QD 与 Playwright 固定版本深入调研](./DEEP_DIVE.md)。其中补充了 QD 的 TLS 校验、跨次 Cookie 复用及导出行为，选型建议以深入调研为准；下文保留第一轮调查记录。

## 一、结论

建议采用 **本地优先、按站点扩展的网页任务执行器**：Playwright 负责页面交互，HTTP 适配器处理经验证可直接调用的请求，持久化任务记录负责每天／每周调度、去重与恢复。

理由是需求已经超出单次签到：不同站点有不同登录过程、多步任务、页面跳转和验证。成熟开源框架值得复用，但本次未找到有充分证据表明可直接满足全部要求的“一键通用方案”。

推荐顺序：

1. 先用 3—5 个真实目标站点验证需求，至少覆盖简单签到、多步任务、人机验证。
2. 简单 HTTP 站点优先评估 QD，避免重复开发现成能力。
3. 若主要需求包含网页交互和人工接管，使用 Playwright 构建轻量本地执行器。
4. 不把通用验证码自动破解作为交付承诺。遇到验证进入等待人工状态；验证后可否继续自动运行，按站点实测。

**“支持各种论坛”应落成“有统一适配协议，可以逐站扩展”，而不是仅输入网址就保证成功。**

## 二、需求与隐私边界

| 需求 | 建议实现 | 必须说明的限制 |
|---|---|---|
| 每日／每周自动执行 | 本地调度＋系统启动保障，时区与补跑规则可配置 | 关机时本机不能执行；休眠后只能在恢复运行后处理 |
| 尽量本地完成 | 本地数据库、本地浏览器、本地日志；无默认云服务 | 访问论坛及认证仍需网络 |
| 可以提供明文密码，但不能外传 | 默认手动登录；可选本地凭据登录模式 | 密码登录必须向指定认证站点发送密码；不能承诺完全不发送 |
| 长期认证 | 按站点／账号隔离浏览器状态或专用用户目录 | Cookie 可过期、被撤销或绑定环境，不能永久有效 |
| 不同签到及每日任务 | 声明式步骤＋代码适配器 | 网站改版和插件差异仍需维护 |
| 外部 API 可选 | 默认关闭，仅接受明确的数据白名单 | 不发送 Cookie、密码、Token、完整 HAR、原始 DOM、截图 |

### 两种认证模式

**模式 A：手动登录、项目不读取密码，建议默认。** 用户在专用浏览器环境完成登录和验证，之后任务复用状态。项目持有的 Cookie 仍属于敏感凭据，必须像密码一样保护。

**模式 B：本地凭据自动登录，可选。** 密码存入系统凭据库或经本地密钥加密的存储，执行时只允许发给已登记的目标认证域名。用户可以明文录入，但没有必要明文落盘。首次录入后页面不回显密码，日志不记录请求正文。

完全断网与在线签到不相容。可以实施的承诺是：**运行时不向第三方泄露凭据，联网用途受限制且可检查。** 安装依赖和下载浏览器属于独立的安装阶段，也应列出来源。

### 如何验证“不外传”

- 任务启动前声明允许访问的论坛、SSO 认证域及必要资源域，用户能查看；跨域跳转重新校验。
- 运行器不携带遥测、远程报错上报或自动上传日志；外部 AI／识别 API 默认关闭。
- 凭据按用途和来源绑定：即使资源域在访问白名单，也不能获得论坛密码或任意授权头。
- 外部 API 若后续确需接入，只允许单独构造的非敏感结构化输入，禁止从页面抓取后整包发送。
- 插件具有与宿主类似的数据访问风险。首版只运行本地审阅并锁定版本的适配器，不在线自动拉取任意脚本。
- 用受控测试账号和合成秘密做网络抓取与日志扫描；检查重定向、WebSocket、异常上报等路径。
- 浏览器请求拦截只是应用层防线，不能代替进程或系统级出站限制；若要求强保证，需另做网络隔离与验证。

不能因为“开源”“本地运行”就声称绝无泄漏。上述措施是待实现和验收的设计，不是当前已兑现的保证。

## 三、开源方案比较

下表“适配成本”和推荐程度是工程判断；项目存在与功能依据链接核实，未进行真实网站运行测试。

| 方案 | 已核实的定位 | macOS / Windows | 对本需求的判断 |
|---|---|---|---|
| [QD / qd-today/qd](https://github.com/qd-today/qd) | HAR 编辑与 HTTP 定时执行框架，MIT | 可评估源码部署；原生安装仍需验证 | 简单签到最值得先试；复杂 DOM 和验证接管需另补 |
| [QD 模板库](https://github.com/qd-today/templates) | 公共 HAR 示例，列有多个论坛模板 | 随执行框架 | 借鉴协议与字段，不能将模板存在等同今天有效 |
| [青龙](https://github.com/whyour/qinglong) | 多语言定时任务管理、日志、通知 | 官方 npm 面板支持 Linux；Mac/Windows 可评估容器 | 已有 NAS／青龙环境时合适；本地新用户偏重 |
| [Automa](https://github.com/AutomaApp/automa) | 浏览器扩展、积木流程、可定时 | 随浏览器，需验证当前扩展兼容性 | 快速手工搭流程的备选；浏览器生命周期影响定时 |
| [Playwright](https://github.com/microsoft/playwright) | 跨平台浏览器自动化，Apache-2.0 | 官方支持 Windows、macOS、Linux | 推荐网页执行基础；本身不是完整签到产品 |
| [checkinpanel](https://github.com/OreosLab/checkinpanel) | 面向定时面板的多站点脚本集合 | 多语言环境，原生跨平台成本不一致 | 参考站点逻辑，不作为新产品主干 |
| [gitcoinkuang/qiandao](https://github.com/gitcoinkuang/qiandao) | Go HTTP 签到控制台，README 宣称单文件跨平台 | 需构建与运行验证 | 轻量 HTTP 备选，不能据宣传推定多步网页可用 |
| [binux/qiandao](https://github.com/binux/qiandao) | 原始 HAR 签到框架，README 指向后继项目 | 不作为首选重新验证 | 了解历史即可，优先考察后继 QD |

### 3.1 QD：适合复用，但不是通用浏览器

原 `qiandao-today/qiandao` 地址重定向至 `qd-today/qd`。其主体是 HTTP 模板执行，而不是完整网页运行环境。[仓库](https://github.com/qd-today/qd)

抽查 [requirements.txt](https://raw.githubusercontent.com/qd-today/qd/master/requirements.txt) 可见 Tornado、croniter、数据库及 pycurl 依赖；[worker.py](https://raw.githubusercontent.com/qd-today/qd/master/worker.py) 可见任务、日志、推送和 Fetcher 结构。这支持将其作为请求调度框架考察，但不构成代码安全审计。pycurl 等依赖意味着不能直接许诺所有 Mac／Windows 环境均可无障碍安装。

模板库存在 3DMGAME、HiFiNi 等条目，但本次没有有效账号进行验证，部分页面索引较旧。HAR 可能包含过期 Cookie、动态参数和第三方请求；导入前需脱敏、逐请求审查、重新提取动态字段。[模板库](https://github.com/qd-today/templates)

适用条件：目标站点主要是查询状态、取 token、提交签到、读取结果，且不依赖挑战验证。若试点符合这些条件，可以直接采用 QD，而无需立刻自研界面。

### 3.2 青龙：调度成熟，网页能力来自脚本

官方说明提供脚本管理、日志和通知，Docker 有 Alpine、Debian 变体；npm 面板部署明确列出 Debian／Ubuntu／Alpine。故“支持 JS/Python”不能推出“面板原生支持 Mac/Windows”。[README](https://github.com/whyour/qinglong)

容器可统一环境，但本地可视浏览器和人工接管更复杂。若后续部署在常开 NAS，可将我们的执行器接入青龙；首版无需强依赖它。框架许可证为 Apache-2.0，社区脚本的许可证和行为需单独核实。[LICENSE](https://raw.githubusercontent.com/whyour/qinglong/master/LICENSE)

### 3.3 Automa：低代码备选

支持连接步骤、表单操作和定时执行，适合少量站点快速搭建；授权采用 AGPL 与商业许可分区，不能按 MIT 项目随意整体复制。[仓库与许可说明](https://github.com/AutomaApp/automa)

扩展定时不能解决机器关机问题；Chrome 的 alarms 文档说明设备休眠时不会被 alarm 唤醒，恢复后才处理错过的触发，持久化行为也与版本有关。这是扩展平台的边界，并非本次实测 Automa 的具体实现。[Chrome alarms](https://developer.chrome.com/docs/extensions/reference/api/alarms)

### 3.4 Playwright：推荐基础组件

支持有界面／无界面浏览器、定位元素、等待状态与复用认证；适合把“进入页面—查看进度—做任务—检查结果”拆为可靠步骤。当前官方安装文档列出 macOS 14+、Windows 11+ 等要求，实施时需要核对用户系统与选定版本，不能笼统承诺所有旧系统。[安装文档](https://playwright.dev/docs/intro)

认证状态文件有冒用账号风险，不应进入版本库；保存状态不代表不会过期。针对 sessionStorage、环境绑定或特殊登录流程要逐站测试。[认证文档](https://playwright.dev/docs/auth)

### 3.5 其他项目与维护证据

checkinpanel 当前取得的提交页顶部记录为 2023-01-04，索引有缓存；只能作为维护风险信号，不能声称实时确认了最新提交。其仓库显示 MIT，同时 README 有额外使用限制文字，复用具体文件前应核对授权。[提交页](https://github.com/OreosLab/checkinpanel/commits/master/) / [README](https://github.com/OreosLab/checkinpanel)

Go 签到控制台的 cURL 导入和轻量部署值得参考，但许可证文件、本轮源码抓取及跨平台运行未完成独立验证；其 README 的高频抢签能力不属于本项目所需。[仓库](https://github.com/gitcoinkuang/qiandao)

QD 最新提交页本次抓取失败，不以项目标题中的版本日期判断停更；Automa 可见 2026 年提交记录，但也不能从提交活跃推导某个论坛兼容。选择时以版本锁定后的试点结果为准。[Automa 提交页](https://github.com/AutomaApp/automa/commits/main/)

## 四、网页机制与适配方式

以下是设计分类，不代表已验证特定论坛产品的所有插件。

| 网站机制 | 执行方法 | 成功判据 | 典型维护点 |
|---|---|---|---|
| 固定签到接口 | HTTP＋会话 | 业务状态＋当天记录 | Cookie、接口字段 |
| 先取 CSRF / formhash 再提交 | 动态提取后请求 | 服务端已签到状态 | token 生命周期、编码 |
| 普通按钮签到 | 浏览器定位与点击 | 页面或接口确认完成 | 文案、DOM、弹窗 |
| JS 渲染、多页跳转 | 浏览器步骤与条件分支 | 最终任务进度 | 异步加载、frame、重定向 |
| 每日／每周多项任务 | 任务图＋独立完成记录 | 每项状态核对 | 部分成功、依赖关系 |
| 阅读或停留任务 | 按站点认可的步骤浏览 | 服务端进度 | 不能用本地计时冒充完成 |
| 答题任务 | 可信答案规则或人工填写 | 平台接受结果 | 题目变化、答案来源 |
| 发帖／评论／点赞／邀请 | 单独任务类型及明确授权 | 目标内容与结果核对 | 不纳入默认自动签到范围 |
| 支付／购买／账号安全修改 | 默认不支持自动执行 | — | 超出签到与常规任务范围 |

同为 Discuz、Discourse、Flarum 或其他论坛，也可能安装不同插件。可复用“论坛家族能力”，但最终需要站点配置，不能只识别建站程序名称。

每日任务的“完成”必须以服务器结果为准。HTTP 200、按钮点击成功、脚本无异常均不足以宣告完成。超时发生在提交之后时，先查询结果再决定重试，避免重复动作。

## 五、人机校验的现实边界

| 类型 | 计划行为 | 能否承诺无人值守 |
|---|---|---|
| 仅首次登录要求验证 | 人工登录，随后复用状态 | 后续是否再次触发取决于站点 |
| 图形文字／简单计算 | 默认人工；必要时研究纯本地识别 | 不预设准确率或稳定性 |
| 滑块、点选、行为验证 | 暂停并通知，在浏览器人工处理 | 不能通用承诺 |
| Turnstile / reCAPTCHA / hCaptcha | 优先人工或站点提供的官方替代认证 | 不能通用承诺 |
| 短信、邮箱、扫码、二次验证 | 人工输入／扫码后继续 | 依赖用户响应 |
| 持续阻断自动化浏览器 | 普通浏览器手工完成该次任务 | 标记手动任务，不反复冲击 |

Cloudflare 官方明确指出自动化浏览器及 Playwright 等框架不支持解决生产挑战。因此“启动真实浏览器即可通过验证”不是可靠产品保证。[支持环境](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)

Turnstile token 有效期为 300 秒且只能验证一次；不能录制一次后每天重放。其 token 也不等于论坛登录 Cookie，不应混淆两种状态。[服务端验证](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)

人工接管分两档：能在当前浏览器通过就恢复流程；当前自动化环境被拒绝时，用户在正常浏览器手工完成，执行器只核对结果或记为手动完成。不能保证在普通浏览器通过后复制 Cookie 必然有效。

第三方验证码服务会增加敏感上下文传输和供应商依赖；与当前本地优先目标不匹配，首版不接入。

## 六、跨平台与定时运行

| 路线 | 优点 | 局限 | 建议 |
|---|---|---|---|
| 本机执行器＋系统启动管理 | 凭据本地，容易人工接管 | 受开机、登录、休眠影响 | 首选 |
| 常开 NAS／自有主机 | 不受笔记本休眠影响 | 迁移凭据、浏览器和网络环境；接管更复杂 | 第二阶段选项 |
| Docker | 环境可重复 | 桌面常驻及 GUI 接管负担 | 可选，不作为首版硬依赖 |
| GitHub Actions | 无需本机常开 | 云端凭据、任务延迟、环境变化 | 不符合默认本地隐私目标 |
| 纯网页／扩展定时 | 接入轻 | 生命周期、后台调度限制 | 少量任务备选 |

Mac 建议用用户级 LaunchAgent 管理本地进程，调度策略在应用数据库持久化。若采用 `StartCalendarInterval`，Apple 文档说明休眠错过的任务在唤醒后运行，但关机错过不会自动按同样方式补齐，所以仍要应用层检查漏跑。[Apple 定时任务文档（归档）](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html)

Windows 用任务计划程序启动／恢复执行器。`StartWhenAvailable` 可帮助补执行适用的时间任务，但有适用条件与延迟，不应当作立即补跑保证；可视浏览器人工接管需要交互式用户会话。[Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings-startwhenavailable)

GitHub 官方说明 scheduled workflows 可延迟甚至丢弃队列任务，公开仓库长期无活动还会禁用定时。因此不作为本项目“每天可靠运行”的默认托管方案。[GitHub 文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

建议默认时区 Asia/Shanghai，支持每站单独设置周期起点，例如每日 04:00 更新、周一 05:00 更新。按站点的业务周期去重，不简单用本机自然日。

## 七、建议架构与用户体验

这是拟议设计，尚未实现。

```text
本地网页：站点 / 登录 / 计划 / 执行结果 / 需要处理
                         │
                    本地任务服务
                         │
       持久化调度 ── 任务状态机 ── 通知与脱敏日志
                         │
                   站点适配器协议
                    /          \
            HTTP 执行器       Playwright 执行器
                    \          /
                 域名策略与凭据隔离
                         │
                      目标论坛
```

建议技术栈：TypeScript＋Playwright＋SQLite＋轻量本地 Web 服务。理由是网页执行与任务逻辑使用同一种语言，跨平台复用较直接；SQLite 保存计划和运行历史，首版不引入 Redis、消息队列或复杂工作流平台。具体库版本在实施阶段锁定。

站点适配器至少定义：站点标识、允许域名、账号引用、认证检查、任务清单、执行步骤、完成判据、周期规则、失败分类、版本与兼容说明。

声明式步骤覆盖 navigate、click、fill、wait、extract、request、assert、branch、manual；复杂场景才用代码插件。填充密码引用凭据标识，不把秘密写入流程文件。请求不得通过 shell 执行用户提供的 cURL。

状态至少区分：待执行、运行中、成功、已完成无需操作、等待登录、等待验证、可重试失败、适配失效、结果未知、已错过窗口。未知结果不可标为成功；等待人工不可无限重试。

用户常见流程：添加支持的站点 → 在浏览器登录一次 → 选择每日／每周计划 → 试运行并核对结果 → 自动执行。失败时显示“为什么失败、下一步怎么处理”，正常完成保持安静。

扩展到每日任务时，每个步骤保存可恢复检查点；浏览器上下文丢失后重新核对页面和服务器状态，不能盲目从旧点击序号继续。

## 八、可靠性与安全实现要点

- 同站点同账号串行，浏览器目录不能并发打开；人工接管也要持有相同账号锁。
- 按站点、账号、任务、业务周期保存唯一运行标识，合并重复触发。
- 对网络错误有限退避；401/403、挑战验证、页面改版不进行无意义重试。
- 把“执行请求已发出但响应丢失”保存为结果未知，再查询状态；无法保证所有外部网站严格 exactly-once。
- 本地面板绑定 loopback，同时具备访问令牌、Origin/Host 校验和 CSRF 防护，不能认为 localhost 天然安全。
- 状态文件、浏览器目录、日志与截图全部排除版本控制；浏览器用户目录可能包含明文数据库，仅加密导出的 Cookie 文件不足以覆盖它。
- 系统账户文件权限及磁盘加密保护浏览器目录；支持删除登录态、清理截图和不含秘密的配置导出。
- HTTP 客户端保持 TLS 证书验证；导入 HAR/cURL 不自动执行，去除无关请求与第三方域。
- 未知网页文案或模型输出不能修改凭据策略、域名白名单、执行权限。
