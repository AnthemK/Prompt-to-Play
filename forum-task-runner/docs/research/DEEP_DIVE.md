# QD 与 Playwright 本地执行器：深入调研

调研日期：2026-10-20。结论依据：固定版本源码静态检查、官方 API 文档及发布信息。没有安装依赖、启动项目、提交签到请求或接触用户账号。

## 结论先行

**对于“本地隐私优先＋长期认证＋多种每日／每周任务”，首选基于 Playwright 的轻量本地执行器；QD 保留为简单 HTTP 签到的备选，不建议未经调整直接接入密码或敏感 Cookie。**

与第一轮相比，决定选型的新证据是：

1. QD 支持条件分支、循环、变量提取和断言，其能力比单次 HTTP 重放强。
2. QD 本轮审查版本在 HTTP 请求构造中设置 `validate_cert=False`，不符合我们要求的 TLS 证书验证基线。
3. QD 定时运行从 `init_env` 和空会话开始；虽然把运行后的会话存入数据库，但该定时路径不自动读回上次保存的会话。不能据此承诺 Cookie 自动滚动续用。
4. Playwright 的浏览器上下文与关联 HTTP 请求上下文能共享 Cookie，适合“人工登录一次—网页或请求执行任务—保存更新后的状态”。
5. Playwright 并非自带安全边界的签到成品。调度、秘密保护、任务恢复与网络策略仍需要开发，不能仅写一个点击脚本就算完成。

## 二、路线 A：复用 QD

### 2.1 实际执行链

```text
数据库中 next 已到期的任务
  → QueueWorker 放入内存队列并按 task_id 加锁
  → 解密模板与初始变量
  → 解释执行请求、if、for、while 等块
  → 提取变量、更新本次运行的 Cookie、检查断言
  → 保存结果与下一次时间
  → 按配置生成日志和通知
```

这是一套有表达能力的 HTTP 工作流框架。它能覆盖“先访问页面拿 token—判断是否完成—提交—查询结果”，不应只把它视作定时 curl。

固定源码定位：

- [模板解释与请求执行：libs/fetcher.py](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/libs/fetcher.py#L721)
- [队列、锁与扫描：worker.py](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/worker.py#L327)
- [到期筛选：db/task.py](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/db/task.py#L93)

### 2.2 定时：能做每日／每周，但要区分“到期执行”和“任务周期”

`Cal.cal_next_ts` 调用 croniter，可表达每日和每周规则。计算依赖进程本地时间；不能直接当作每站独立 IANA 时区实现。[libs/funcs.py](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/libs/funcs.py#L498)

从 `next <= now` 扫描可推断：进程恢复后，保留在数据库里的到期任务有机会再次被调度。但它不等于“逐个补齐历史周期”，也不自动知道某论坛凌晨 04:00 才换日。提交后崩溃、尚未更新数据库时，再运行是否重复，需要模板先查服务端状态。

观察到的锁是按任务 ID 的进程内字典。同一账号的两个不同任务没有因此自动共享账号锁；不能把它当作跨进程锁或业务去重。

对我们的影响：简单签到可以在模板中先检查已签到；多项每日任务仍要设计周期键、账号串行和结果未知状态。

### 2.3 Cookie：本次请求链可复用，跨次滚动续期存在缺口

`Fetcher` 使用 CookieJar 处理请求与响应 Cookie；这有利于同一轮多步请求。

但定时 `BaseWorker.do`：

- 以解密后的 `task['init_env']` 建立变量；
- 初始化 `session=[]`；
- 成功后加密并保存本轮变量和 session；
- 下一轮同一入口仍从初始变量与空 session 开始。

这不是说 QD 不能使用 Cookie：用户可以把 Cookie 放进初始变量或模板。区别在于服务器更换 Cookie 后，**这条运行路径没有自动将上轮 CookieJar 作为下一轮起点**。凭据稳定的简单站点可能照常工作；要求长期自动续期的站点需要明确改造和验证。[worker.py 208—229 行附近](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/worker.py#L208)

修补时不能盲目把所有运行变量写回初始配置：一次性 CSRF token、临时响应和业务计数应与认证状态分开。

### 2.4 对本需求最重要的安全发现

以下是源码观察，不是完整漏洞审计，也没有进行攻击验证。

| 观察 | 影响 | 接入真实凭据前的处理 |
|---|---|---|
| HTTPRequest 构造设置 `validate_cert=False` | HTTPS 不再具备我们要求的证书真实性验证 | 改为验证证书，分别验证 Tornado 与 PycURL 路径；无效证书应失败 |
| 默认监听 `0.0.0.0`，示例 Compose 映射 `8923:80` | 不符合仅本机访问的默认目标 | 原生绑定 loopback；容器端口映射限制宿主 `127.0.0.1` |
| 默认 AES 与 Cookie 密钥来自固定字符串 `binux` | 默认密钥不能保护敏感部署 | 安装时生成独立密钥，和备份分离保管 |
| 模板／任务导出先解密再生成 JSON | 导出物可能携带密码、Cookie、变量 | 默认做无秘密导出；含秘密备份单独加密 |
| 模板可自行构造 URL、请求头和正文 | 不可信模板能够把变量发往不期望的目的地 | 导入审查、目标域校验、秘密用途绑定 |
| 错误、`__log__` 和通知内容来自流程 | 模板把秘密写入内容时可能进入日志或推送 | 关闭外部通知，限制可记录字段并测试异常路径 |

依据：

- [请求构造与证书开关](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/libs/fetcher.py#L170)
- [默认监听和密钥](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/config.py#L17)
- [示例容器配置](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/docker-compose.yml)
- [导出路径](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/web/handlers/user.py#L522)
- [日志与推送内容](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/worker.py#L247)

数据存储并非全部裸明文：用户数据通过用户密钥加密，用户密钥再由应用主密钥解密；但运行服务本身必须能解密，因此不能抵御恶意模板或已被控制的宿主进程。[db/user.py](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/db/user.py#L148)

没有证据支持“QD 默认偷偷上传账号”这种说法。已核实 Google Analytics 的配置默认为空，基础页面只有启用该配置时才插入 GA 脚本。订阅下载和通知则是另外的出站渠道，需逐项关闭或控制。[页面模板](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/web/tpl/base.html#L116)、[订阅实现](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/web/handlers/subscribe.py#L95)

### 2.5 成功判定与每日任务扩展

QD 的 `run_rule` 起始状态为成功，配置的成功／失败断言负责修正结果；多个成功断言按“任一匹配”通过。因此不能只导入请求而省略明确完成判据，也不能误认为多个成功断言必须全部满足。[断言实现](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/libs/fetcher.py#L324)

HTTP 多步骤任务可以继续使用 QD；需要点击页面、等待 JS 控件、接管浏览器时，额外接一个浏览器服务会产生两套状态和调度协调问题。对目前的个人本地工具，不建议先做“QD＋浏览器微服务”再解决双系统复杂度。

### 2.6 部署与可复现性

Python 原生部署仍需验证依赖安装，尤其是 PycURL；容器减少环境差异，但增加 Mac／Windows 桌面运行负担。

值得注意的是，检查到的 `Dockerfile.lite` 构建过程使用浮动基础镜像并另外从 Gitee 拉取项目。**即使固定了 Dockerfile 所在提交，也不能据此认定镜像里的应用就是这个提交。** 若选择 QD，需要固定实际源码、依赖和基础镜像摘要；或独立核对发行镜像内容。[Dockerfile.lite](https://github.com/qd-today/qd/blob/c3b6068561d063a0a0e4be224b039007bebe9e8b/Dockerfile.lite)

### 2.7 采用条件

QD 适合以下组合：主要是稳定 HTTP 请求、验证少、可接受导入或维护模板、需要尽快得到已有面板。

它不再是“无需改动即可满足隐私要求”的选项。最低准备包括：TLS 校验、本地绑定、独立密钥、模板出站限制、日志／导出处理、Cookie 生命周期验证。如果真实网站还要求复杂页面操作，继续改造 QD 的收益会降低。

## 三、路线 B：Playwright 本地任务执行器

### 3.1 已有组件与需要开发的部分

| 已可复用 | 仍需开发 |
|---|---|
| 浏览器启动、元素定位、等待、frame／弹窗操作 | 本地任务面板和站点接入向导 |
| 隔离 BrowserContext、认证状态导入导出 | 加密存储、密钥管理、账号生命周期 |
| 与页面共享 Cookie 的 HTTP 请求能力 | 每日／每周持久化调度与补跑窗口 |
| 页面／网络诊断能力 | 业务成功判定、账号锁、部分完成恢复 |
| Windows／macOS 支持基础 | 两平台安装、启动、升级和实机验证 |

建议直接使用 Playwright 库执行生产任务，把 Playwright Test 用于测试。测试运行器的整项重试不应直接等同于有副作用任务的业务重试。

### 3.2 认证应提供两种状态保存方式

**优先：新建隔离上下文＋显式保存 storageState。**

适合 Cookie／localStorage 等即可恢复的站点。执行结束后原子保存最新状态；根据站点需要启用 IndexedDB 保存。状态可在内存中序列化并加密后落盘，不必直接把明文 JSON 长期写入项目。

**备用：每个站点／账号独立持久化浏览器目录。**

适合需要更完整浏览器环境的站点，但目录内的数据不等于全部被应用加密。需要文件权限与磁盘保护，而且同一目录不能同时启动多个浏览器实例。不能直接借用用户平时使用的默认 Chrome 主目录。[BrowserType 文档](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context)

sessionStorage 不在标准状态持久化方案中自动处理；若站点依赖它，需要专用保存／恢复逻辑。Cookie 轮换、撤销、IP 或设备绑定仍可能使状态失效。[认证文档](https://playwright.dev/docs/auth#session-storage)

**修正第一轮措辞：**“工具不读取密码”应理解为实现上不采集、不记录密码，而不是技术上完全没有读取能力。浏览器自动化和站点页面本身有接触输入内容的能力。手动登录时应停止 trace、截图、录制与正文日志；Cookie 仍在工具信任范围内。

### 3.3 浏览器与 HTTP 混合执行，不需要两套登录

固定版本的 `BrowserContextAPIRequestContext` 将读取／更新 Cookie 委托给所属浏览器上下文。于是同一任务可以先在页面登录，再通过关联 request 查询任务状态或提交允许的操作；服务器返回的新 Cookie 也进入同一上下文。[fetch.ts](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/fetch.ts#L705)

这为长期认证提供了可用基础，但自定义头里的 token、localStorage token 和 CSRF 值不会自动变成正确的 API 请求参数，仍需适配器处理。

建议顺序：优先把真实网页流程跑通，再将稳定且可验证的步骤替换为 HTTP。不要为了减少一次浏览器操作，过早维护一套脆弱的私有接口。

### 3.4 网络隐私需要三层设计

| 层 | 建议 | 不足 |
|---|---|---|
| 浏览器页面层 | 上下文级路由检查目的地，按需处理 WebSocket；默认阻止 Service Worker 后验证站点兼容性 | 不能当作全进程防火墙 |
| HTTP 执行层 | 统一 request 包装器；保持 TLS 校验；敏感请求关闭自动重定向并逐跳审核 | 独立 Node 请求不会因此自动受浏览器路由约束 |
| 进程／系统层 | 如要求严格限制联网，另做出站代理或 OS 级限制，覆盖浏览器后台和插件进程 | 跨平台配置成本高；需要专门验收 |

官方说明 `BrowserContext.route` 不拦截被 Service Worker 接管的请求，WebSocket 也有专门路由 API。不能只安装一个 `route('**/*')` 就宣称网络被完全限制。[BrowserContext 文档](https://playwright.dev/docs/api/class-browsercontext#browser-context-route)

HTTP 请求默认验证 TLS，默认允许自动重定向。固定 v1.64.1 源码在跨 origin 重定向时移除标准 Authorization，并移除原 Cookie 头后重新处理 Cookie；因此不能断言它会无条件转发这两类凭据。但是自定义 token 头和保留正文的重定向仍需要我们自己的目的地策略。[重定向实现](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/fetch.ts#L458)

密码输入页面还可能加载第三方脚本；同源脚本能接触输入，不会因为脚本最初来自第三方就被自动隔离。即使我们的工具不采集密码，也不能替整个目标论坛承诺如何处理密码。可控制的是工具自身的数据流、允许的联网目的地和本地持久化。

默认不接入任何模型 API。将来如需辅助识别非敏感任务文本，应通过单独的无凭据模块发送人工可查看的白名单字段，而不是把原始页面或截图上传。

### 3.5 怎样支持“不同的每日任务”

建议站点适配器定义五类职责：

1. `checkAuth`：检查账号身份及认证是否有效。
2. `inspect`：读取当前业务周期和每项任务进度。
3. `plan`：仅产生尚未完成的必要步骤。
4. `executeStep`：执行一个有明确后置条件的步骤。
5. `verify`：从服务端或页面可靠状态确认完成。

任务规范应另外声明周期、允许域、凭据引用、超时、可重试性、是否需要人工及副作用类别。步骤类型可覆盖导航、点击、输入、提取、请求、等待、判断和人工节点。

示例场景只是设计说明，不声称某个真实网站已适配：

| 流程 | 正常执行 | 恢复方式 |
|---|---|---|
| 每日点击签到 | 检查当天状态→点击→查询记录 | 先查记录，已完成则不点击 |
| 每日领取三项奖励 | 分别查询每项资格与领取状态 | 只继续未确认领取的项目 |
| 每周多页任务 | 根据站点周起点计算周期→逐项完成 | 保留任务项检查点，重新读取页面 |
| 人工滑块／扫码 | 等待用户→重新核对认证／任务进度 | 过期则重新发起页面流程，不复用旧 token |

“等待 30 秒”不是完成证明；“没抛异常”也不是完成证明。无法核实的状态必须保留为未知。

### 3.6 调度与恢复的具体方案

数据库至少区分账号、任务定义、运行记录和步骤记录。以 `(site, account, task, period)` 作为业务去重键；运行锁按账号，而非仅按任务。

系统启动管理只负责拉起本地服务，由服务调度器检查到期计划。每天／每周规则使用明确时区，补跑只针对仍有效的当前业务周期。不要默认补执行错过的所有历史周期。

崩溃恢复分两类：

- 只读步骤：通常可重新读取。
- 已发出修改请求、结果未保存：先查询结果，无法查询则等待人工判断，不能直接重复。

数据库事务不能覆盖外部论坛的提交操作，所以无法单凭本地唯一键保证外部 exactly-once。任务图与幂等检查必须共同发挥作用。

### 3.7 人工接管与诊断

需要验证时保留账号锁并暂停自动动作；用户完成后重新检查状态。后台无界面浏览器不能简单变成同一个有界面窗口；若切换模式需要重建上下文，页面临时状态可能丢失。容易触发验证的站点可直接使用有界面模式，具体体验在试点验证。

自动化浏览器被站点拒绝时，降级为普通浏览器人工完成，而非承诺复制 Cookie 后一定恢复。Cloudflare 的限制见第一轮报告。

trace 对调试有帮助，但包含浏览器操作和网络活动，启用选项后还包含截图与页面快照。建议默认只写结构化事件日志，登录阶段关闭 trace，必要诊断仅本地短期保存，不自动附加到通知或上传。[Tracing 文档](https://playwright.dev/docs/api/class-tracing)

## 四、两条路线直接比较

下表是结合源码的工程判断，不是运行评分。

| 维度 | QD | Playwright 本地执行器 |
|---|---|---|
| 最快获得现成界面 | 强，已有面板 | 需开发轻量界面 |
| 简单 HTTP 签到 | 强 | 能完成，但要编写适配 |
| JS 页面和多步交互 | 非主要能力，需外接 | 核心优势 |
| 每日／每周调度 | 已有 cron 与到期扫描 | 需要持久化调度模块 |
| Cookie 跨次更新 | 本轮运行入口有缺口 | 可利用状态快照与关联请求上下文 |
| 人工验证接管 | 没有在所查执行链中发现完整浏览器接管能力 | 可设计，但需处理会话与资源生命周期 |
| 当前隐私目标 | 要调整 TLS、配置、模板、日志和导出 | 可从需求设计，但仍必须测试 |
| 模板／插件信任 | HTTP 模板本身可使用秘密发送请求 | 代码插件可访问进程能力，首版仅可信插件 |
| 本地跨平台体验 | Python 依赖或容器需验证 | 基础支持较直接，安装和系统调度仍需验证 |
| 长期维护 | 上游框架＋本地补丁＋模板 | 自有小核心＋站点适配器＋上游 Playwright |

**最终建议：主线选 Playwright；QD 只保留一个受控 HTTP 试点，不同时建设两套正式系统。** 如果后续提供的站点实际上全是简单接口，再考虑转向 QD。

暂不引入通用 AI 浏览器代理。已知站点每天重复的任务更适合确定性流程；遇到改版应明确报错。后续 AI 可以辅助生成适配器草稿，但不直接持有凭据或决定任意操作。

## 五、后续验证应解决什么

以下是将来的实验清单，本轮没有执行。

| 实验 | QD 关注点 | Playwright 关注点 | 通过条件 |
|---|---|---|---|
| Cookie A 被服务端替换为 B | 修补后下次是否使用 B | 保存／恢复后是否使用 B | 第二次运行无需重新登录 |
| 本地测试服务提供无效 TLS 证书 | 原版与修订版的差异 | 保持默认校验 | 不继续认证请求 |
| 请求跳转到第二个受控域 | 模板和跳转策略 | 标准头、自定义 token、307/308 正文 | 非批准域无秘密 |
| 成功页面没有出现但 HTTP 200 | 模板断言是否齐全 | verify 是否拒绝成功 | 不能误报 |
| 提交后进程退出 | 下次扫描是否重复 | 运行记录恢复逻辑 | 先查询后决定下一步 |
| 每周任务跨周／休眠恢复 | 进程时区和 next 行为 | 周期键、补跑窗口 | 不执行过期周期动作 |
| 多任务共用同一账号 | 是否需要补账号锁 | 账号锁和目录锁 | 无并发覆盖认证状态 |
| Service Worker／WebSocket | 不适用或需独立能力 | 拦截覆盖与站点兼容 | 网络记录符合策略 |
| 导出、日志、错误、trace | 明文 JSON 与模板日志 | 浏览器诊断内容 | 默认输出不包含测试秘密 |

先在受控本地样例验证核心机制，再使用真实站点验证业务。受控实验通过不能替代真实验证码测试；单次真实成功不能替代连续运行观察。

对原路线图的调整：P0 增加版本和出站证据检查；P1 提前验证 Cookie 轮换与秘密输出；P2 保留业务周期与崩溃恢复；P3 再扩展复杂任务。界面开发仍放在核心执行闭环之后。
